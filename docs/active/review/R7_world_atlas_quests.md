# R7: World, atlas, quests

Read 2026-11-07 on `main` 18fd3e7f (reviewer, Fable 5.1; two Sonnet surveys, one of Region layout
generation and one of the hex world; two Sonnet verifiers). Area per the concept doc:
`src/systems/world`, `src/systems/atlas`, `src/systems/quests`; the questions are generation cost,
caches and retired-concept code.

## Summary for the owner

**What this area does for the player.** The world map around the Guild Hall (127 hex cells in six
rings, generated once at a new game), settling a place on it (which lays out a whole new mat:
Tokens, ground, water, stone), travelling between the Regions the guild has settled, and the
quests: the cartographer's tutorial chain and the bounties the Hall posts, which live as Tokens on
the mat.

**How healthy it is: good.** Everything here is seeded (no `Math.random` anywhere in the three
folders), nothing runs per tick except the quest clock, the world is generated in milliseconds and
kept whole, travel never regenerates anything, and the architecture map's counts for these
folders are exact. The costs are in two places the player waits anyway (settling a place, the open
world map), and the housekeeping is mostly migration code written for saves that the version
check already refuses, plus the usual export residue.

**The three findings that matter most.**
1. **Migration code for saves that can no longer load** (CR4-072): the quest system still
   carries a path that turns a save's sidebar quests into Tokens, and the save loader still drops
   Vault, currency and cartographer fields, all written for saves older than the current schema
   version, which refuses every such save at the door. Nothing can reach them.
2. **Settling a place lays the mat out up to nine times, and each candidate pond rasterises the
   whole water field** (CR4-073): the one place a player waits on generation, and nothing has
   timed it.
3. **The open world map recomputes every cell's price and lock on every Bank change**
   (CR4-074): 127 cells, each asking every hero's skill levels and rebuilding the star table,
   with the Region list rebuilt several times per pass; only while the Atlas is open.

**Counts.** 6 findings: 2 `cleanup`, 2 `perf` (reasoned, P3), 1 `bug` (P3), 1 `docs`;
0 `owner-decision`. Verified: see each finding's `Verified by`.

**Measure first.** `console.time` round `Atlas.settle` on a Riverside and a Highland cell in a
dev build (and `Settling.seedFor`'s try count), and `worldView()` with the Atlas open on a game
with six Regions and eight heroes.

### CR4-076  Two settle-time placements use `Math.hypot` and trigonometry, against the layout's own determinism rule
- **Tag**: bug
- **Priority / Effort / Risk**: P3 / S / low

- **What**: The layout code promises that a seed gives the same mat on every machine, and keeps that promise in `Layout.js`, `WaterShapes.js` and `StoneShapes.js`, and breaks it in two places that also run once at settle and store their result: the Starter Camp's stone centre is accepted or rejected by a `Math.hypot` comparison, and a settled place's arriving enemies are placed by sine, cosine and `Math.hypot` from the place's seed. ## Notes (no `path:line` of their own, or another area's)

- **Per tick, checked.** The only per-tick work in the three folders is `QuestTokens.tick` (`:409-438`): two `filter`s over the cached Token list (`questTokens`, `bountyTokens`) and two tuning reads (`questCap`, `questIntervalMs`) per tick, then nothing unless the clock laps. `QuestManager.reportProgress` and `syncCollections` filter the Token list once per event they hear (`SPRITE_COLLECTED`, `CYCLE_COMPLETE`, `INVENTORY_UPDATED` among them), each O(Tokens) with a small constant; a kept set of quest Token ids would make all of them O(quests). Not filed: on a 128-Token mat it is microseconds.
- **Generation that is fine.** The hex world: 127 cells, generated once at a new game in milliseconds (`generate.js`; `ringOf` rescans the cells per call, `:252`, 6× per ring, and the extras step tries 32 draws per cell, both trivial at this size); `rollWorld` checks up to 20 seeds on the new-game screen and keeps the cleanest. `createWorld` (`World.js:94-103`) does not run `findingsOf`, so a world started from an unrolled seed is unchecked; today every seed comes through `rollWorld`. Travel (`Atlas.travel`) regenerates nothing: one JSON round trip of the leaving board (`:486`) and the stored ground. `regionGround` is decoded once per stored map (`regionGround.js:17-24`, a `WeakMap` keyed by the stored object, so it dies with the save it came from).
- **Caches, checked.** `Settling.js:58`'s materials memo is module-level and never cleared: keyed by Token type id, bounded by the registry, stale only if the registry changed under a running game, which it cannot. `worldView.js:20`'s standing-Token cache is keyed by the world object. `RegionRules.installed` and `Arrival`'s subscriptions are reset on every apply and teardown. No cache in the three folders grows without bound.
- **Randomness, checked.** No `Math.random` in `src/systems/world`, `src/systems/atlas` or `src/systems/quests` except the bounty generator (`questBounties.js:65-71,81,84,98`, by design: "the order of its `Math.random` draws is part of the bench's identical-work gate") and the `random = Math.random` defaults of `QuestTokens.spawnQuest`, `spawnBounty` and `tick` (`:230,256,409`). The world, the layout, the water, the stone, the names: all `mulberry32` on a seed or a seeded hash. Three live-state inputs can make two machines lay out one seed differently by design: the per-device `nearRadius` (`layoutInputs.js:41-49`, only when a Token has a `Cannot` rule), the content registry, and each Token's sprite name.
- **`Atlas.travel` publishes `STATE_CHANGED`** (`Atlas.js:499`), the retired event's last publisher: T-195, already ticketed (R1).
- **The quest clock's design is sound**: closed form, holds at the cap, drops the leftover, retries a tutorial step only when the board changed (`owedOn`, `:359-378`): the pattern R2 asked for elsewhere.
