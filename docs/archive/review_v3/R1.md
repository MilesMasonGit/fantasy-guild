*Review session, 2026-09-28. Tickets CR3-100 to CR3-110. No game code changed; no spike worktree was created.*

**What was measured, and how far to trust it.** Engine measurements were taken at commit `0641600`.
`main` has since moved to `f9af6ba` (the P3 merge), which changed **no engine file**. That merge only

## 1. Plain-language summary for the owner

- **A brand-new game is not really saved for its first ten minutes.** The game writes the save slot
  *before* it puts the Guild Hall, the Forest, the Mine and the starting items on the table. If the game
  crashes or the PC loses power in those ten minutes, the slot reopens as an empty table with no Guild
  Hall. I reproduced this in the engine. The fix is small. (CR3-100, P1)
- **Changing the computer's clock breaks the game clock.** Setting the clock back 5 seconds while
  playing makes every working station "start a new cycle" again, every tick, for a while: 127 starts in
  5 seconds instead of 4. Any hero gear that fires "when a cycle starts" fires and pays each time.
  Setting the clock forward an hour puts an hour into the Time Bank. Reproduced. (CR3-101, P1)
- **The engine clock itself is fine.** Ten ticks a second on a timer is not what makes the game slow,
  and nothing in the loop needs redesigning. What is slow is the work *inside* a tick, and that belongs
  to R2 and R3.
- **Where a realistic tick goes (S2):** about half goes to spawners checking themselves (CR3-047), about
  a third goes to stations re-checking their charges and neighbours every tick, and the rest is walking,
  flags and fights.
- **On the big board (S3), about 60 % of the tick is "a message was sent, so rebuild the neighbourhood's
  buffs"** (CR3-102). Merging duplicate rebuilds within one tick would cut the worst freeze from 275 ms
  to roughly 65 ms, but it would not fix the common one-in-a-hundred stutter. That needs R2's fix.
- **The message system itself costs nothing measurable.** About 6 messages a tick at about 40
  nanoseconds each. Bringing back "event batching" would not speed the engine up.
- **Saving is quick and not on the tick.** An autosave takes about 0.7 ms on a realistic board and
  about 1.2 ms on the torture board, every 10 minutes. It could be made about 2.5× faster cheaply
  (CR3-109, polish).
- **Debug logging is not a problem.** It makes about one call every 8 ticks, and a released build
  prints nothing. (CR3-030: close.)
- **The order the engine's nine systems run in each tick is mostly irrelevant.** Only "quests after the
  board" makes a measurable difference, and a harmless one. It should be written down explicitly.
- **The event list (`boardEvents.js`) is mostly honest.** It has one dead event, several incomplete
  descriptions and a stale header. 16 engine events are sent with nobody listening (§4).

**Is per-tick event coalescing worth reintroducing? No, not as a bus feature.**

1. **The bus itself is free.** It costs 12 ns per publish with no subscriber and 43 ns with one (1 M
   publishes, scratch harness). 6.15 events per tick is about 0.25 µs, roughly 0.02 % of an S2 tick.
2. **The UI already coalesces what matters.**
   - Per-Token events are routed by id (`tokenEvents.js:35-70`).
   - `useGameState` batches with `queueMicrotask` (`useGameState.js:97-111`).
   - React 19 batches `setState` calls made within one task.
3. **The one real gain is deduplicating rebuilds** (CR3-102), and that belongs inside `TileModifiers`,
   not in the bus:
   - S2: 16 of 3000 ticks had two or more neighbourhood rebuilds. Deduplicating would save 0.007 ms per
     tick.
   - S3: 2 of 500 ticks had two or more. The worst tick was **274.6 ms, with 4 whole-mat rebuilds
     taking 255 ms**. The next worst was 193.7 ms, with 3 rebuilds taking 188 ms. Each would be about
     65–85 ms with one rebuild.
   - The p99 ticks (80–117 ms) each carry **one** rebuild, so coalescing does not move p99.

### CR3-100 — A new game's first save has an empty table: no Guild Hall, no starting items, for up to 10 minutes
- **Category / Severity / Effort**: CON+WIRE · **P1** · S
- **Impact / Confidence / Score**: 5 · 1.0 (reproduced headless) · 5.0
- **Risk**: low. Add one save after the opening Tokens are placed. Needs test: a new-game test that reads the stored slot back (none exists).
- **Where**:
  - `ReactRoot.jsx:161-170`: `newGame(index)` runs first, then `publish('react:slot_selected')`.
  - `SaveManager.js:269-279`: `newGame` calls `save(false)` straight after `GameState.initNew()`.
  - `EngineBootstrap.js:297-299`: `createDefaultGameData()` places the Hall, Forest and Mine and fills the Bank later, inside the `react:slot_selected` subscriber (`main.jsx:115`).
  - The next save is the autosave, 10 minutes later (`SettingsManager.js:69`, `SaveManager.js:87`), or `beforeunload` (`:93`).
- **What**: the save that claims the slot is written before the starter set exists. If the game dies in
  its first 10 minutes without a clean close (crash, power loss, Task Manager, or a desktop shell that
  does not fire `beforeunload`), loading that slot gives an empty table with no Guild Hall and an empty
  Bank. Nothing on the load path re-creates the opening set: `openingMat()` is only called from
  `createDefaultGameData`. With no Hall there is no way to recruit a hero, so the slot is dead.
- **Evidence**: scratch harness, doing exactly what `handleSlotSelect` does and then `onSlotSelected(0, true)`:
  - claim save: **0 Tokens, 0 Bank items**;
  - live state after boot: Guild Hall, Oak Forest, Copper Mine, and 3 item stacks;
  - stored slot after boot: **still 0 Tokens**;
  - autosave interval: 600,000 ms.

  Not tried in the real game (no dev server in this session). I did not check whether Tauri fires
  `beforeunload` on window close.
- **Fix sketch**: in `onSlotSelected`, call `SaveManager.save(false)` right after `createDefaultGameData()`. Alternatively, move the claim save there.
- **Owner session**: R1
- **Status**: 🔲 Open

### CR3-101 — The tick trusts the wall clock: a clock step backwards replays cycle starts, a step forwards fills the Time Bank
- **Category / Severity / Effort**: CON · **P1** · S–M
- **Impact / Confidence / Score**: 4 · 1.0 (reproduced headless) · 2.0–4.0
- **Risk**: medium. The tick-clamp tests drive time through `vi.spyOn(Date, 'now')` (`TickDeltaClamp.test.js:31`), so they must move to the new clock. Offline accrual must keep using the wall clock.
- **Where**:
  - `TimeManager.js:62-79`: `update()` uses `Date.now()` and clamps only from above (`Math.min(scaled, MAX_TICK_DELTA_MS)`). A negative delta passes straight through.
  - `GameLoop.js:69-84` passes that delta to every handler and publishes `time_overflow`.
  - `BoardRunner.js:730-741`: `CYCLE_START` and `LoadoutMoments.fire(…'CYCLE_START')` fire whenever `cycleElapsedMs` is not above 0.
- **What**: a backward step (the user changes the clock, or Windows time sync steps it) makes one tick's
  delta negative. Every working Token's progress goes below zero. Every tick until it climbs back above
  zero counts as "a new cycle begins": `CYCLE_START` is published, and the hero's carried
  `CYCLE_START` rules run and **pay their costs** (`LoadoutMoments.js:66-81`). A forward step is
  clamped to 1 s, and **the rest is banked as Time Bank time** (`TimeBankManager.js:44`). That is
  dormant while the Bank's spend UI is off (CR2-141), and an exploit when it returns.
- **Evidence**: S2, same board, 50 ticks each:
  - **4** `CYCLE_START` in the control run; **127** after a 5 s backward step;
  - first delta after the step: −4,900 ms;
  - a 1 h forward step banked **3,599,100 ms**.
- **Fix sketch**: use `performance.now()` (monotonic) for the in-session delta in `TimeManager.update`,
  and floor the delta at 0. Keep `Date.now()` only for `savedAt` and offline accrual. This is owner
  question Q1, because it changes what "time away with the game open" means.
- **Owner session**: R1
- **Status**: 🔲 Open

### CR3-102 — On large boards most of the tick runs inside synchronous event subscribers, and one tick can rebuild the whole mat several times
- **Category / Severity / Effort**: HPB · P2 (the target miss is already ticketed as CR3-004) · M
- **Impact / Confidence / Score**: 4 · 1.0 (measured) · 2.0
- **Risk**: medium. Deferring a rebuild changes *when* a buff turns on within a tick. Needs a test pinning "a buff applies to work done in the same tick as the change", or an explicit ruling that one tick of delay is fine.
- **Where**:
  - Subscribers: `BoardRunner.js:782-784` (`ADJACENCY_DIRTY` → `TileModifiers.rebuildAround`) and `TileModifiers.js:125` (`HERO_MOVED` → rebuild).
  - Publishers inside the tick: `EnemyMotion.js:230` (every finished stroll), `HeroMotion.js:291` (every arrival), `Flags.js:223`, `BoardCombat.js:543-544` (every kill).
  - `EventBus.js:52-74` delivers synchronously and in place.
- **What**: the bus runs each subscriber in place, so a stage that publishes `ADJACENCY_DIRTY` or
  `HERO_MOVED` pays for the rebuild on the spot. With a board-reach rule on the mat, every such rebuild

- **Hypothesis to test**: a per-tick dirty-point set in `TileModifiers`, flushed once at the start of the
  Token loop and once at the end of the tick, cuts the S3 **max** by about 3× and leaves p99 unchanged.
- **Owner session**: R1 (contract); fix with R2's CR3-004 work
- **Status**: 🔲 Open

## 8. Owner questions (multiple choice, recommendation first)

**Q1: How should the game measure time while it is open? (CR3-101)**
- **(A) Recommended: a stopwatch that cannot go backwards for time while playing; the wall clock only
  for time away while the game was closed.** Changing the PC clock stops affecting the game while it
  runs. The closed-game Time Bank works exactly as now.
- (B) Keep the wall clock, but ignore negative jumps. This is a smaller change. Setting the clock
  forward would still fill the Time Bank.
- (C) Leave it. The bug is rare, but it replays "cycle starts" and pays their costs when it happens.

**Q2: A stalled station's "Out of item" news: how often should it be said? (CR3-005)**
- **(A) Recommended: once, when the problem starts, and again only if it clears and comes back.** The
  red mark on the Token stays the whole time, so nothing disappears from the player's view.
- (B) Repeat it every few seconds as a reminder. It costs a little, and the red mark already reminds.
- (C) Keep it every tick (today's behaviour: ten times a second, with no visible difference).

**Q3: When one change should update buffs across the whole table, may that update land a tenth of a
second later? (CR3-102, decide together with R2's CR3-004)**
- **(A) Recommended: yes, within the same tick.** Merge duplicate rebuilds and do the one rebuild at a
  fixed point in the tick. It is invisible to players, and it caps the worst freeze at about a third.
- (B) Yes, and on very large boards spread the rebuild over a few ticks. That gives the smoothest
  frames, but a buff may take up to about 0.3 s to switch on everywhere.
- (C) No. Keep rebuilding the instant anything changes, and rely only on making each rebuild cheaper (R2).

**Q4: The unused pieces of the clock (TimeManager's own timer and pause, time counters that nothing
reads, the "card use" tally). (CR3-105)**
- **(A) Recommended: remove them, but keep `window.Game` and the loop's replaceable entry points that
  the bench and the Perf HUD use.**
- (B) Keep them as groundwork for a future pause button.
- (C) Remove only the per-tick writes and leave the unused functions.
