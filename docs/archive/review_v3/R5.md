## 1. Plain-language summary for the owner

**Why the Perf HUD says the mat redraws ~40 times a second.** Two separate
things are going on, and only one of them is the "whole mat" problem.

1. **Hero sprites animate by redrawing through React, 8 times a second each.**
   Every hero on the mat, and every hero in the dock, flips to its next
   animation frame by telling React "my picture changed". With the game
   *stopped* (no ticks at all), the mat still redrew **~42 times a second**
   and the dock **~43 times a second** — all of it hero sprite frames. Each
   of those redraws is tiny (about 0.1 ms), but the HUD counts every one, so
   **the §4.4 target "mat ≤ 1 redraw a second" can never pass while sprites
   animate this way**. (CR3-301)
2. **The whole mat really does redraw on most ticks — because goblins walk.**
   When an enemy takes a step, the mat's master list of Tokens changes, so the
   whole mat is rebuilt: sorted again, every hero and flag redrawn, and the
   Tokens the goblin passed redrawn. On the realistic board this happened on
   **265 of 300 ticks (8.8 times a game-second)**, and **239 of those 265 were
   caused by enemy steps alone**. Each costs ~3–5 ms of React work in the dev
   build. This is pre-filed CR3-008; it is now **measured, and a P1**.

The "top event" P3 saw, `board:progress` (~35 a second), turned out to be
**innocent**: it causes no mat redraws at all. The progress rings paint
themselves without React.

**A real bug the player can see (CR3-300): the dock's HP bars are wrong.** The
dock figures read each hero in the one way the code's own rules forbid
(the "CR-044" trap). Result: an HP change alone never redraws the bar. I
caught it live: a hero at **87 / 144 HP was drawn at 35 %** (the HP they had
some time earlier), and changing their HP and announcing it changed nothing on
screen until an unrelated field changed. The Bank's hero panel has the same
flaw. Small fix.

**Clicking things redraws every Token (CR3-302).** Anything that changes the
top-level screen state — inspecting a hero, selecting a Token — rebuilds all
~108 Tokens, because the top of the app hands the mat brand-new functions each
time. One such click cost **34 ms** of React work (dev build). Small fix.

**`state_changed` (the "something changed, everyone re-check" broadcast)** is
much less of a problem than feared at realistic load: it fires only **0.23
times a game-second**, never causes a mat redraw by itself, and costs **3.7 ms
(105 Tokens) / 6.1 ms (320 Tokens)** of re-checking per firing (dev build) —
roughly linear, **not** the feared Tokens² blow-up. But five other events are
broadcast to every Token the same way; together that is ~2 firings a second,
each a 1–4 ms spike. **29 of the 31 engine places that send `state_changed`
already send a specific event right before it**, so it can be retired in
stages. (CR3-304, CR3-305)

**Rules in the wrong layer.** No component decides whether a *game* action is
legal on its own — the engine re-checks every command. But:
- the engine **cannot start a game without React** (`react:slot_selected` is
  its only start signal; CR3-307);
- React publishes engine events in three places and announces one engine
  command's change on the engine's behalf (CR3-306);
- three small rules are copied into components (CR3-308).

**Subscriptions are clean.** Every one of the 44 subscriptions in the UI is
paired with an unsubscribe. No leaks found.

**Tickets: 12** — P1 × 2, P2 × 6, P3 × 4. Two owner questions (§9).

## 3. The MatBoard re-render trigger table (measured)

### 3.1 Method

No game file was edited. In my own preview tab, on `/?stress=realistic`
(S2: 105–108 Tokens, 8 heroes, 6 goblins) and `/?stress=torture` (S3: 320
Tokens), I injected at runtime:

- a wrapper on `window.Game.EventBus.publish` logging each event name;
- a **fiber walk** from the React root that records, per function component,
  whether its hooks list (`memoizedState`) or props object changed since the
  last look — i.e. *whether the component function actually ran* — grouped by
  the Perf HUD's `<Profiler>` surface;
- a read of `MatBoard`'s four `useGameState` slices (hooks 13, 22, 30, 38:
  tokens, heroes, flags, terrain) to see **which selector returned a changed
  value**, and a field-level diff of what changed;
- ticks driven one at a time with the real loop stopped
  (`GameLoop.runHandlers(100)`, then yielding with `MessageChannel` so React
  commits before the next tick). Rates are **per game-second** (10 ticks),
  independent of the pane's throttling.
- per-component render cost from React's own profiling fields
  (`selfBaseDuration`) on the fibers that ran.

**Totals, S2, heroes working (300 driven ticks):** `MatBoard` itself rendered
**265 times = 8.8 per game-second** (cause: enemies only 239, heroes only 10,
both 14, another Token change 1, nothing 35). Add ~42/s sprite commits and the
HUD's "MatBoard ~40/s" is fully explained. A second 50-tick sample while a
goblin was walking every tick: **50/50 ticks**, 63 subsurface commits.

**While heroes walk** (all 8 flags swapped across the mat, 40 ticks): tokens and
heroes slices changed on **40/40** ticks; `MatToken` renders rose to **7.7 per
tick**, 161 of 175 caused by `z` alone (dense z-ranks shift when the worked
band changes, `matLayers.js:83-109`).

**S3 (321 Tokens, heroes walking, 20 ticks):** heroes slice changed 20/20;
`MatBoard` render ~7 ms per commit (dev), of which only ~3 `MatToken`s ran.

|---|---|---|

### 3.4 Selector fan-out and deep-equal cost

Cost of one bare publish, from `publish` until React has committed, loop
stopped, nothing actually changed (dev build, median of 15–20):

| Event | Subscribers S2 (105 Tokens) | ms S2 | Subscribers S3 (320) | ms S3 |
|---|---|---|---|---|
| `state_changed` | 133 | **3.7** | 348 | **6.1** |
| `board:tile_changed` | 115 | 2.3 | 330 | 5.4 |
| `token_placed` | 110 | 2.2 | 325 | 4.5 |
| `board:hero_moved` | 118 | 1.5 | 333 | *49 — see note* |
| `board:alert_changed` | 106 | 1.2 | — | — |
| `board:token_charges_changed` | 106 | 1.1 | — | — |
| `board:enemies_walked` / `heroes_walked` / `heroes_updated` | 1 / 9 / 12 | 0.1 | — | — |

- **Not quadratic.** 3× the Tokens cost 1.65× the time. The per-spawner
  `SpawnerSystem.spawnerCounts` walk (CR3-009's worry) does not show at 320
  Tokens.
- **The deep-equal is not the cost.** Building the 321-entry tokens slice takes
  0.078 ms; a field-by-field compare of two of them 0.016 ms. The cost is the
  number of selectors: ~0.02–0.03 ms × one per Token × every broadcast event.
- **One publish, many firings, one pass:** `useGameState` coalesces with
  `updateQueued` (`useGameState.js:99-101`), so 40 `state_changed` in one tick
  (CR3-255's loot sweep) run each selector **once**. The residue is the
  publish loop itself: 0.7 ms per `state_changed` at S2 (dev), so a 40-pile
  sweep is roughly 28 ms of synchronous publishing inside that tick —
  *estimated from the per-publish median, not measured as a sweep*.
- ⚠ **Note for R2/R3 (not R5's):** at S3 a bare `HERO_MOVED` cost **49 ms**,
  all in one engine subscriber, `TileModifiers.js:125-130`
  (`rebuildAround([left, now])`). My payload was empty, so this may be the
  "no point" path; real payloads name the hero. It is consistent with CR3-004
  and worth one real-payload measurement by the owner of that ticket.

### 3.5 HeroDock

HeroDock's ~29–43 commits/s are **all** dock `AnimatedHeroSprite` frames. Its

### CR3-300 — The dock's HP bars (and the Bank hero panel) show stale hero data
- **Category / Severity / Effort**: RC+UX · **P1** · S
