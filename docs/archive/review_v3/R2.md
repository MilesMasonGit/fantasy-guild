## 1. In plain language

- **The one big slowdown has a safe fix, and it has been tried.** The engine asks
  "give me every Token, in order" about 47 times a tick and rebuilds the list
  every time. Keeping one list and rebuilding it only when a Token arrives or
  leaves made the realistic board's typical tick **~40 % faster** (1.50 → 0.95 ms)
  and cut the one-in-a-hundred slow tick roughly in half. The game did exactly
  the same work: same end state, same test results.
- **What makes that list go stale is short and known.** Four functions in one
  file (`BoardState.js`) are the only things that put a Token on the mat or take
  one off. A move doesn't count, because moving never changes the order. §3 lists
  them.
- **Most of those 47 requests come from the spawners** (31 of 47, counting how
  many trees are on the mat), not from the board's own code. R3 has designed the
  spawner fix. It uses the same counter as this one, so the two fixes fit
  together.
- **Pushing Tokens aside became 4–5× faster, with identical results.** When a
  spawner has to shove its neighbours, one arrival took ~27 ms typically and up to
  56 ms. With three small changes that do the same arithmetic in a cheaper order,
  it takes ~5 ms, and 13 ms at worst. Every Token ended at exactly the same
  point, down to the last decimal (checked with a checksum of every position).
  Shrinking the mat went from 333 ms to 73 ms, also identical.
- **The target is still missed in two places.** The worst push is 13 ms, against
  8. Most of what remains is the neighbourhood rebuild that R3 has already
  spiked. Shrinking the mat is 73 ms against 8, but only the developer Mat Tuner
  can shrink the mat. I've asked you whether the 8 ms rule applies there (Q1).
- **The benchmark's "0 of 50 player drops landed" is correct behaviour, not a
  bug.** The spot it aims at is buried under a cluster about 310 units wide, and
  the nearest free spot is 285 units away. A drop may only be nudged 160 units,
  so every drop flies back, as FP-46 says. The scenario only ever measures
  refusals, so it should also measure drops that land (§6, CR3-156).
- **One behaviour surprise.** When an arrival pushes, it can also shove Tokens
  **on the other side of the mat** that were already overlapping something. Walking
  enemies overlap things all the time. When a Token grows or transforms, the Tokens
  it can shove include ones you placed. Nobody reported this, but it goes against
  "shove *nearby* Tokens aside" (FP-17). Your call (Q2).
- **No leaks found.** Hero bodies, enemy bodies, claims and the neighbour cache are
  all released or bounded. The 8-hour run's flat memory agrees.
- **The `BoardCombat ↔ Flags` import loop** is two loops. Each can be cut with a
  few lines and no change in behaviour (§6, CR3-157).

### 3.2 Do callers mutate the returned array?

**No.** All 40 production call sites (`grep BoardState.tokens()` over `src/`) do
`for…of`, `.filter`, `.find`, `.map` or `.length`. The eight places that hold
the result in a variable were read: `BoardRunner.js:531`,
`UpkeepSummary.js:102`, `MatSummary.summariseMat` (`MatSummary.js:42-72`, from
`MatCapBadge.jsx:58`), `useUIModals.js:18`, `useDisallowMode.js:64`,
`MatBoard.jsx:85`, and four tests. None of them writes to the array.
**Proven by spike A:** the cached list was `Object.freeze`d, so any write
would throw in these strict-mode modules. The whole suite ran with it: 3,438
tests passed, the same 10 known failures, and nothing threw.

Two behaviours the cache **must** keep:

1. **Snapshot iteration.** `BoardRunner.js:537` and the test helper
   `tests/fixtures/mat.js:51` iterate the list while Tokens are added or removed
   (depletion, spawns, `removeToken` in the loop). Today each call returns a fresh
   array, so iteration runs over a snapshot. The cache keeps this only if it
   **replaces** the array on a change and never patches it in place (no `splice`
   on remove). Spike A does this.
2. **No UI selector may return the list itself.** It holds live instances whose
   `x`/`y` change without a new array, so a selector returning `tokens()` would
   deep-compare equal to itself and miss moves. Today none does:
   `MatBoard.jsx:85` maps into new objects, and the others reduce to numbers.
   Worth one line in the `tokens()` JSDoc.

### 3.3 Is the `placedAt` tie-break stable?

**Yes, and a cache reproduces it exactly.**

- `placedAt` comes only from `stampOrder` (`BoardState.js:147-149`), which uses
  the board's `nextTokenOrder` counter. So it is unique per board. It is set only
  when missing, so a moved or lifted-and-replaced Token keeps its place. Nothing
  else writes it (`grep "placedAt\s*="` → only `:148`).
- Ties are possible only for instances with no `placedAt` (`?? 0`). That happens
  only on hand-built test boards that assign `board.tokens` directly. `Array.prototype.sort`
  is stable, so ties fall back to `Object.values` insertion order. That order
  changes only when `addToken` replaces a *different* object under the same id
  (`:209`), which is an add, so it rebuilds the cache.
- The cache builds its list with the **same expression** as today
  (`Object.values → filter(typeId) → sort(placedAt)`), so every rebuild gives the
  same order. Spike A confirmed this: S2, S3 and S4 ended with the same
  fingerprints as the clean run, and the S4 position checksum matched.

### 3.4 The shape

```js
// BoardState.js — beside layoutVersions (:159)
const membershipVersions = new WeakMap();          // keyed by the board.tokens object
function bumpMembership(b) { membershipVersions.set(b.tokens, (membershipVersions.get(b.tokens) || 0) + 1); }

let tokenListCache = { tokens: null, version: -1, list: Object.freeze([]) };

/** Every Token on the mat, in arrival order. ⚠ Shared and frozen: iterate it, never
 *  mutate it, and never return it from a UI selector (instances move in place). */
export function tokens() {
    const map = board()?.tokens || null;
    if (!map) return EMPTY;                          // a frozen []
    const version = membershipVersions.get(map) || 0;
    if (tokenListCache.tokens === map && tokenListCache.version === version) return tokenListCache.list;
    const list = Object.freeze(Object.values(map)
        .filter(t => t?.typeId)
        .sort((a, b) => (a.placedAt ?? 0) - (b.placedAt ?? 0)));
    tokenListCache = { tokens: map, version, list };  // REPLACE, never patch
    return list;
}
```

**Keyed on membership, not on `layoutVersion`.** `layoutVersion` also counts
moves, and enemies move almost every tick, so a cache keyed on it would be
rebuilt nearly every tick. A move can't change arrival order, so the membership
counter is enough. With it, S2 rebuilt the list **0.006 times per tick**
(measured). This is the same counter R3 wants for the spawner census (R3 §3.1,
CR3-047), so **one counter serves both fixes**.

### 3.6 The neighbour cache (CR3-200's fix, in R2's files)

R3 filed CR3-200 and proposed per-move invalidation. R2 agrees and adds the exact
shape:

- Key the whole-cache drop on **membership + board identity + Near radius**
  (today it uses `layoutVersion`, `nearby.js:169-173`).
- A move invalidates only the Tokens whose Near set can change. `BoardState`
  records a per-board **move journal**: `setTokenPoint` appends
  `{id, from, to}` and bumps a position counter. On its next read, `neighbourIds`
  replays the journal entries it hasn't seen and deletes the cached entries of
  `id` and of every Token within `nearRadius() + 1` of `from` or `to`. That is the
  same "both ends" rule `rebuildAround` uses (`nearby.js:122-137`). The `+1` is
  slack: rebuilding an extra entry is harmless, but missing one gives a silently
  stale recipe or tool answer.
- `BoardState` can't import `nearby.js` (that would be a cycle), which is why
  it's a journal the reader pulls rather than a callback.
- Order inside each cached list stays arrival order, which is unaffected by
  moves.

R3 measured a membership-keyed (not exact) version bringing S2 p99 from 1.75 to
1.34 ms. The per-move version should land close to that and stay exact.

## 4. CR3-003 — the push solver and the nudge search

### 4.1 Where an arrival's time goes (measured, S4, before any fix)

Hooks in the worktree timed each part of 50 pushing arrivals and the shrink.

| Part | Share of 50 arrivals | Notes |
|---|---|---|
| `relax` (the push solver, `MatPlacement.js:374-451`) | **77 %** (2,644 of 3,415 ms) | 10–30 passes per push (median ~19), and **23–67 Tokens moved per push**. The whole cluster shifts. |
| first `findSpot` within nudge reach (`EffectActions.js:197`) | 5 % | always fails in S4 (the cluster is full), about 3,400 candidates |
| fallback `findSpot` within 640 u (`MatPlacement.js:361`) | **0 %** | never ran: every push succeeded |
| the rest: `besideBearer`/`openness` (8 × whole mat), `placedTokenIds`, `checkPlacement`, `applyPushes`, `rebuildAround` | ~18 % | `rebuildAround` is CR3-004 (R3) |

**The shrink (338 ms at baseline) is not the push solver at all.**
`MatResize.fitToMat` (`MatResize.js:93-108`) makes one `findSpot` per stranded
Token with a 320 u reach. On the 20 → 6 shrink that is **130 searches, 92 of
which fail**. A failing search tries every one of about 13,400 candidates, each
against about 100 neighbours. Those searches are **96 % of the shrink** (465 of
484 ms in the probe run). The single `ADJACENCY_DIRTY` rebuild afterwards is 30
ms.

### 4.2 Why `relax` is slow

- **All Tokens on the mat are bodies** (`:375-377`). There's no region limit, so
  each pass visits every pair: 135 bodies means 9,045 pairs.
- **Each pair that isn't fixed-fixed calls `minGap`** (`:388`). That is two
  `hitRadiusOf` calls, each an `artRadiusOf` (a registry lookup) plus
  `isSmallToken` (another lookup), plus two `matTuning` reads. Four lookups per
  pair per pass, when the answer depends only on the two types.
- **`Math.hypot` runs for every pair** (`:391`), before the cheap test that
  throws away almost all of them.
- **The early exit already exists** (`:420`: `if (!moved) break`), so this is
  not "30 passes every time". The passes that do run average about 19, because a
  packed cluster really does need them.
- **The final check is another all-pairs loop** with `minGap` per pair
  (`:428-436`).

### 4.3 The cheapest fix with identical results (spike B)

All three changes do the same arithmetic in the same order, or skip only work
whose outcome is already certain:

1. **Hit radius per body, once.** Store `h = hitRadiusOf(typeId)` on each body
   and compute `gap = (a.h + b.h) * factor`, where
   `factor = 1 - matTuning('overlapPct')/100` is read once. This is exactly
   `minGap`'s expression (`MatPlacement.js:76-78`), with the same operands in the
   same order, so the result is bit-identical. Applied to both the pass loop and
   the final check.
2. **Axis rejection before `hypot`.**
   `if (dx >= gap || dx <= -gap || dy >= gap || dy <= -gap) continue;`
   If |dx| ≥ gap then hypot ≥ gap, so `d*d >= gap*gap - EPS` and the original
   would `continue` too. The same holds for the final check's `distanceSq`.
   Exact.
3. **The nudge search** (`findSpot`/`whyRefused`/`findSpotAnywhere`):
   - (a) `contextFor` buckets its prefiltered neighbours into cells as wide as
     the widest gap. `clearOf` then checks only the 3×3 cells round a candidate.
     Its answer is "is any neighbour too close", and check order can't change
     that, so the result is exact. The plain scan stays below 16 neighbours.
   - (b) The mat-edge bounds (`artRadiusOf`, `matW`, `matH`) are read once per
     search instead of once per candidate (`insideMat :89-95` inside `legalIn
     :212`).
   - (c) Each ring's `cos`/`sin` table is computed once, **with the same
     expression**, and cached (`candidatesAround :460-469`).

The spike diff was 98 lines added and 12 removed across `BoardState.js` (spike A)
and `MatPlacement.js` (spike B). It is recorded in §5; nothing else changed.

## 8. Owner questions (parked, multiple choice, recommendation first)

**Q1 — Does the "≤ 8 ms per shrink" target apply to the developer Mat Tuner?**
Only the Mat Tuner (a developer panel, `matTuning.js:1-23`) can shrink the mat.
After the exact fixes, a 20 → 6 shrink with 135 Tokens takes 73 ms: one
noticeable hitch, once, when a developer drags a slider.
- **(A) Recommended: no. Keep 8 ms for everything a player does (drops, arrivals,
  pushes) and exempt developer-panel actions.** Nothing further to do for the
  shrink.
- (B) Yes, 8 ms. This needs a search that gives up early on a full mat. That
  changes *where* crowded Tokens end up after a shrink (still on the mat,
  never lost).
- (C) Decide later, if mat size ever becomes a player upgrade that can shrink.

**Q2 — When an arrival pushes, should it move only the Tokens it is actually
crowding?** (CR3-151) Today a push also separates every other overlapping pair
on the mat: a goblin standing on a tree across the mat, or, when a Token grows,
one of your placed Tokens a goblin was standing on.
- **(A) Recommended: limit a push to the newcomer and whatever it pushes into,
  in a chain.** This matches FP-17's "nearby". It's also the cheapest push
  possible (CR3-152 would never be needed). Saved layouts don't move. Only
  *future* pushes behave differently, and only when unrelated overlaps exist.
- (B) Also leave walking enemies out of pushes. They stroll over Tokens by
  design (HM-3), so treat them like flags: no footprint.
- (C) Keep today's behaviour exactly. It's the only option with identical results
  to today, which the brief required for the speed work (the speed fixes above
  keep it either way).
