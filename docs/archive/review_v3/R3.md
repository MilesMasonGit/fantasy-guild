## 1. In plain language, for the owner

**The good news first: two small fixes make the realistic late-game board meet
its engine target, and they don't change what happens in the game at all.**

1. **Full spawners were doing a lot of pointless work.** A Forest that already
   has all its trees still "tries" to spawn ten times a second, and each try
   counts every Token on the mat twice. On top of that, a second pass every tick
   re-counts every spawner's family again to decide whether to show its warning
   badge. Together that was the biggest single job in the realistic tick
   (about 0.9 ms of 1.5 ms). The fix is to count the mat **once**, and count it
   again only when a Token arrives or leaves. In the spike, that job fell from
   **0.94 ms to 0.15 ms per tick**, and the game did *exactly* the same things —
   same Tokens, same charges used, same Bank, same hero XP, to the last unit.
2. **Buff bookkeeping was quadratic.** Every time the game refreshes the buffs
   on one Token, it walked *every* Token on the mat looking for buff-givers —
   even though a realistic mat has only two or three buff-givers. The fix is to
   keep a short list of just the Tokens that give buffs. In the spike, the
   one-in-a-hundred slow tick with a whole-mat aura on the board fell from
   **~15 ms to ~2.2 ms**, and the worst tick from **~25 ms to ~5 ms**. On the
   300-Token torture board the worst tick fell from **~250 ms to ~30–45 ms**.
   Again, identical game results.

With both spikes, the realistic board's slow tick went from **~3.6 ms to
~1.8–2.2 ms**. A third, separate problem (item 3 below) is what stands between
that and the **1.5 ms** target — an experiment shows fixing it would land at
about **1.3 ms**.

3. **Walking enemies throw away a useful memory every step.** The engine
   remembers "who is near whom" so stations don't have to measure it again —
   but it forgets *everything* whenever *any* Token moves, and walking enemies
   move every tick. So that memory is almost never used (CR3-200). It belongs to
   R2's files, and I've written what the fix must keep true.
4. **Things that wait for room re-run the expensive "find a spot" search every
   tick.** A spawner boxed in by your own Tokens, or a Foundation waiting for
   room to build, runs the placement search ten times a second. That search can
   take tens of milliseconds on a crowded mat (CR3-201). Not yet measured,
   because no benchmark board has such a stuck Token.
5. **Two things you can author don't work where they appear to.** An item's rule
   can be given almost any "when…" moment in the editor, but carried items only
   ever fire on two of them (CR3-202). And there is still **no safety net** in
   the game screen: one UI error blanks the whole screen while the engine keeps
   running (CR3-203) — the black-screen crash from the handoff is fixed at its
   source, but the net that should catch the next one was never added.
6. **Already-known items confirmed:** the input-cost discount is used when paying
   but not when deciding whether a station can start (CR3-028 — confirmed); a
   crafted Token with no charge count still arrives with unlimited charges, and
   now one of your recipes actually makes one (the Copper Woodaxe) (CR3-045 —
   needs your decision).

**Nothing here changes a design decision.** Three questions for you are in §7.

## 3. Fix designs

### 3.1 CR3-047 — capped spawners, and `syncAlerts`

**Why a capped spawner retries every tick.** A spawner is one row of
`TimedChanges.HANDLERS` (`TimedChanges.js:234-242`). When its clock falls due,
`attemptSpawn` runs; at cap it returns `null` (`SpawnerSystem.js:201`), and
`advance` then holds the clock **full** (`TimedChanges.js:289-293`) so the
attempt is due again next tick. That is deliberate and documented
(`TimedChanges.js:57-62`): it is what makes a spawner fire **on the first tick
after** a tree is cut. The cost is not the retry — it is what each retry does:

* `countOf` → `BoardState.tokens()` + filter (`SpawnerSystem.js:128-131`);
* `capOf` → `liveSpawners()` → another `tokens()` + an `isSpawner` test per
  Token, then `familyOf` (fresh arrays and Sets) per spawner
  (`SpawnerSystem.js:123-125, 138-145`).

**Why `syncAlerts` costs as much as the attempts.** It runs once per tick
(`TimedChanges.js:326`) and calls `liveSpawners()` (one full scan), then
`spawnerStatus` for **every** spawner, each doing its own `countOf` + `capOf`
(`SpawnerSystem.js:350-362, 264-279`) — 1 + 2·S whole-mat scans per tick. With
S = 8 that is 17 of the 47 `tokens()` calls per tick; the attempts add ~14.
Measured (S2 profile, probes added in the spike): **`advance` 0.43 ms, of which
`attemptSpawn` 0.38; `syncAlerts` 0.43 ms** — the alert sync is half the stage.

**What invalidates "at cap".** The family count and the cap are pure functions
of *which Tokens are on the mat* (their `typeId` and `turnedFrom`) and of the
content definitions. So "at cap" can change only when:

| Cause | Where it happens | Goes through |
|---|---|---|
| A family member leaves (cut out, killed, binned, removed, grown/turned into a non-family type) | `Charges.destroyToken`, `DiscardBin.binToken`, `Placement.removePlacedToken`, `EffectActions.transformInstance` | `BoardState.removeToken` |
| A spawner arrives, leaves, turns, or turns back (cap changes) | placement, bin, transform | `addToken` / `removeToken` |
| A spawn lands (count changes) | `EffectActions.spawn` | `addToken` |
| A load / new game / hand-built board | new `board.tokens` object | object identity |
| Content changes (`allowance`, `spawns`, `grows.into`) | `registerTokenTypes` (tests), a CMS re-sync + reload | registry |

**Moving does not.** I checked: nothing outside `BoardState` writes
`board.tokens` (`BoardState.js:202-233`; the only other writer is the dev
`TestDashboard.jsx:265`, which replaces the object — covered by identity), and
nothing mutates an instance's `typeId` or `turnedFrom` in place (a change is
always remove + add, `EffectActions.js:399-405`).

**The design — a census, keyed on membership.**

1. `BoardState` gains a **membership version**: a counter bumped in `addToken`
   (when the id is new to the map) and `removeToken`, kept per `tokens` object
   exactly like `layoutVersion` (`BoardState.js:152-169`), but **not** bumped
   by `setTokenPoint`. (The existing `layoutVersion` is bumped by every enemy
   step — `EnemyMotion.js:277` — so keying on it would rebuild the census every
   tick; still a big win, but needlessly so.) This belongs to R2's file and is
   the same counter CR3-001's cached `tokens()` list wants: arrival order is
   `placedAt`, which a move never changes, so that cache too only needs
   membership. **One counter serves both fixes.**
2. `SpawnerSystem` keeps one `census = { tokens, version, countByType, spawners,
   caps }`, rebuilt lazily in one pass when the membership version (or the
   board object) changes. `countOf(family)` sums `countByType`; `capOf` is
   memoised per family key inside the census; `liveSpawners()` returns
   `census.spawners`; `familyOf` is memoised per spawner type.
3. `syncAlerts` keeps its shape — it simply becomes cheap because
   `spawnerStatus` is now two map reads plus, only when not at cap,
   `missingUpkeep`.
4. The content case: memoised families must be dropped when the Token registry
   changes. Today nothing in the game changes content at runtime (a CMS sync
   reloads the page), and Vitest isolates modules per file, so the spike did
   without it — but the real fix should key the family memo on a registry
   version (bumped by `registerTokenTypes`) so a test that re-registers a type
   mid-file cannot see a stale family.

**Why this spawns at exactly the same moments.** The attempt still runs on every
due tick, in the same Token order, at the same point in the tick; only the
*answer* to "count" and "cap" is looked up instead of recomputed, and the lookup
is invalidated by every event that could change it — including a spawn earlier
in the same pass (it bumps the version, so the next spawner re-counts). No
`random` is consumed differently (the cap test precedes `pickWeighted`,
`SpawnerSystem.js:201-204`). **Proven in the spike**: identical end-state
fingerprints on S2, S3 and S5 (§4).

**Not recommended:** skipping the attempt while "at cap" and waking it on an
event (`TOKEN_DEPLETED`, `TILE_CHANGED`…). Equivalent in theory, but it trades
a counter that every mutation already passes through for a list of events that
must stay complete — the "wired at one end" failure this codebase keeps paying
for.

Also, cheaply, in the same slice: `advance` allocates `{def, active}`, a
filtered handler array and a `Set` for **every Token every tick**
(`TimedChanges.js:246-249, 264`) even though most Tokens have no clock. Measured
after the census: `advance` 0.06 ms/tick for 107 Tokens — not worth a change
now; a per-type "has any timed block" memo would remove it if CR3-001's work
makes it visible.

### 3.2 CR3-004 — `rebuildAll` is quadratic without an aura

**Why.** `rebuildToken(id)` iterates `applicableStatements(id)`
(`TileModifiers.js:421-454`), which for **one** Token:

* calls `nearby(self.id, REACH.NEARBY)` — `tokensWithin` → a full
  `tokens()` copy + filter + **sort**, then a full distance pass
  (`TileModifiers.js:349`, `nearby.js:75-84`);
* then walks **every** Token again (`TileModifiers.js:352`) — another
  `tokens()` sort — reading each one's statements.

So one rebuild is O(N log N) and `rebuildAll` (`:605-609`) is O(N² log N)
regardless of any aura. The aura only decides *how often* the whole mat is
rebuilt (`rebuildTokens`, `:568-577`); it cannot change the cost of one. The
same scan also runs **twice per completed cycle** (`collectItemGrants`,
`collectStatusApplications`, `:465-529`, called from `BoardRunner.js:379, 409`)
and once more per `rebuildTokens` call in `boardReachOnBoard` (`:536-542`).

Almost all of that walking is wasted: a Token can only contribute if it carries
an **ambient** statement (`Provides`/`Grants`/`Applies`, no `When`,
`:62, 381-382`). The S2 board has 2 such Tokens out of 109.

**The design — an ambient-source index (recommended), a spatial query later.**

1. Keep, keyed on the same **membership version** as §3.1, the list of Tokens
   (in arrival order) whose type carries at least one ambient statement, plus a
   `hasBoardReach` flag. Types are static between content loads; membership is
   the only thing that changes the list; a move does not change arrival order.
2. `applicableStatements` iterates **that list** instead of `tokens()`, and
   computes the relation per source directly — `SELF` by id, `NEARBY` when both
   centres exist and `distanceSq ≤ nearRadius²` (exactly `tokensWithin`'s test,
   `nearby.js:55-58, 78-81`), else `DISTANT`. No `nearby()` call, no sort.
3. `boardReachOnBoard()` returns the index's flag.
4. As in §3.1, key the index on the registry version too, so a content reload
   cannot leave a newly-authored buff out of the list.

Cost per rebuild becomes O(S) (sources); `rebuildAll` O(N·S + one sort).

**What must stay true, and why it does.**

* **"Departure AND arrival"** (Free Playmat 1.3, `TileModifiers.js:584-588`,
  `nearby.js:121-137`): the fix changes *how* a Token's buffs are computed,
  never *which* Tokens get rebuilt. `rebuildAround`, `tokensAround` and every
  caller passing `[from, to]` are untouched. ✅
* **Board-reach correctness** (`:555-577`): every board-reach *ambient* source
  is in the index, is reached as `DISTANT`, and `reachCovers(BOARD, DISTANT)`
  is unchanged. The departure case still works because `boardReachLive` is
  still remembered from the previous rebuild. ✅
* **The `noStackDuplicates` guard** (`:367-391`) depends on *arrival order* of
  sources; the index is a filter of `tokens()`, so order is identical. ✅
* **Modifier order inside an aggregator** is the same for the same reason. ✅
* Tokens with statements but no ambient ones were `continue`d past without
  touching `seenTypes` before, so dropping them from the walk is exact. ✅

**Optional second step — rebuild the whole mat less often.** With a board-reach
aura present, `rebuildTokens` rebuilds everything on every `ADJACENCY_DIRTY`
(every enemy stroll, `EnemyMotion.js:230`). A distant Token's board-reach inflow
can only change when the *set* of board-reach sources or their paid state
changes (`isStatementPaid`, `BlockUpkeep.js:67-70`); a filter on the target is
evaluated against the Token itself, which is inside the rebuilt ring whenever
it changes. So "whole mat only when the board-reach signature (ids + paid
flags) changed" is exact. **Not spiked, and not needed**: after step 1, S5's
7.5 rebuilds per tick cost 0.04 ms. Keep it in the drawer for S3-size boards.

**Remaining super-linearity.** The micro-bench board puts one buff on every
fifth Token (`bench/micro/engine.bench.js:27`), so there S ≈ N/5 and
`rebuildAll` stays N·S. A spatial query (CR3-003, R2) for `NEARBY` sources
would make that O(N · nearby sources + board sources). Realistic mats don't need
it yet.

## 5. Tickets

### CR3-200 — Every enemy step throws away the neighbour cache, so each station check re-scans the mat
- **Category / Severity / Effort**: HPB · **P1** · M
- **Impact / Confidence / Score**: 5 · 1.0 (measured) · 2.5
- **Risk**: medium — a cached neighbour list that outlives a move is a silently wrong recipe/tool/wear answer; needs a test that moves a provider out of Near and checks the station stops seeing it (CR3-041's harness)
- **Where**: `nearby.js:166-180` (`neighbourIds`, keyed on `BoardState.layoutVersion`); `BoardState.js:235-243, 178-179` (`setTokenPoint` → `bumpLayout`); `EnemyMotion.js:277` (a `setTokenPoint` per enemy step); consumers in R3: `Charges.contextProvidersAround` via `planCycle` (`Charges.js:302-303, 359-361`), `RecipeResolver.contextTiersAround`/`typesNear`/`servesFrom`/`wearNearbySupport` (`RecipeResolver.js:69-100, 237-336`), reached from `WorkCheck.fixableReason` (`WorkCheck.js:64-84`)
- **What**: the cache "is dropped the moment the layout changes" — any Token put down, **moved** or removed. Walking enemies move every tick, so on any board with enemies the cache is emptied before every tick and each lookup becomes `nearby()` → `tokens()` copy + sort + distance pass. This is also the answer to the brief's WorkCheck question: **work is checked once per worked Token per tick** (`BoardRunner.js:626`), plus once per un-staffed Token carrying a fixable skip (`BoardRunner.js:605-607`), plus a flag's candidates only when it chooses (`Flags.js:556`, 0.19 evaluations/tick) — so on a choosing tick a Token is checked twice, otherwise once. Its cost is not duplication; it is `planCycle` → `neighbourIds` missing the cache. Each check allocates the resolved-IO object, one or two context-tier objects (`contextTiersAround` runs in both `checkAcceptedTokens` and `unmetContext`), a providers array, the plan's `debits`/`missing` arrays and the input-check result.
- **Evidence**: S2 profile — `neighbourIds` 10.1 calls/tick, **9.5 of them misses** (`nearby.nearby` 9.48 calls/tick); `fixableReason` 0.28 ms/tick of which `planCycle` 0.26. S3: `fixableReason` 2.0–2.8 ms/tick, the largest R3 stage after the spikes. Experiment C (cache keyed on membership, not exact) cut `fixableReason` to 0.034 ms/tick and **S2 p99 from 1.75 to 1.34 ms** — under the §4.4 target of 1.5 ms, which spikes A + B1 alone do not reach.
- **Fix direction (for R2, who owns the files)**: invalidate per move, not globally — on `setTokenPoint(id)`, drop the cache entries of `id` and of every Token within Near of its old or new point (the same "both ends" rule as `rebuildAround`); keep the global drop for add/remove/radius change. With CR3-001's membership counter this is a few lines.
- **Owner session**: R2 (fix) · R3 (consumer, filed here)
- **Status**: 🔲 Open

### CR3-201 — Anything waiting for room re-runs the placement search every tick
- **Category / Severity / Effort**: HPB · P2 (reasoned) · M
- **Impact / Confidence / Score**: 4 · 0.6 · 1.2
- **Risk**: medium — must retry at exactly the same moments (a Foundation builds, a spawner spawns, the first tick room exists)
- **Where**:
  - a spawner with room under its cap but nowhere to land: `attemptSpawn` → `EffectActions.spawn` → `spawnPoint` → `MatPlacement.findSpot`, then `forceSpot` (the push solver) (`SpawnerSystem.js:207-216`, `EffectActions.js:190-203`), retried every tick because the clock is held full (`TimedChanges.js:288-293`);
  - a Foundation holding `NO_ROOM`: `Foundations.hasRoomToBuild` → `forceSpot` every tick (`BoardRunner.js:702-706`, `Foundations.js:41-48`), and again inside `completeCycle` when it is due (`BoardRunner.js:218-222`);
  - a station whose recipe outputs a Token, holding `NO_ROOM`: `hasRoomForTokenOutputs` → `Placement.hasRoomForProduct` → `findSpotAnywhere` every tick (`BoardRunner.js:709-712, 169-176`, `Placement.js:350-355`).
- **What**: the "held full, retried next tick" pattern that CR3-047 found for the cap also applies to "no room" — and here each retry is a placement search, not a count. S4 measured a pushing arrival at **28 ms typical, 59 ms worst**, and a refused player drop at ~2 ms; a failing `forceSpot` has not been measured. None of the bench boards has a Token stuck for room, so the bench cannot see this yet.
- **Hypothesis to test**: add a scenario (or an S2 variant) with one Forest ringed by placed Tokens and one Foundation with no room; expect a per-tick cost in the milliseconds, flat for as long as it waits.
- **Fix direction**: remember the failed verdict per `(Token, target typeId)` keyed on the layout (plus mat size and `nearRadius`), and re-run the search only when the layout changed. `pickWeighted` must still be called on every attempt so the random stream is unchanged (`SpawnerSystem.js:204`); the NEAREST_FREE search itself consumes no randomness (`EffectActions.js:196-203`). ⚠ Keyed on today's `layoutVersion` this would rarely hit on a board with walking enemies — it wants the same per-region invalidation as CR3-200.
- **Owner session**: R3
- **Status**: 🔲 Open

### CR3-202 — An item's rule can be given moments that carried items never fire
- **Category / Severity / Effort**: WIRE+UX · P2 · S
- **Impact / Confidence / Score**: 3 · 0.6 · 1.8
- **Risk**: low
- **Where**: `LoadoutMoments.js` `fire` matches `statement.when.event !== eventId` (`:57-60`); it is called with exactly two ids, `'CYCLE_START'` (`BoardRunner.js:737`) and `'COMBAT_ENGAGED'` (`BoardCombat.js:432`); `LiveEffects.js:203` fires `EFFECT_TICK` for carried *effects*. The editor offers **every** moment to every bearer: `statementSlots.js:98-99` (`momentOptions` = all of `TRIGGER_EVENTS`), `:527-540`. The audit has the mirror-image check for Tokens only (`ContentAudit.js:476-494`, `EFFECT_TICK` on a Token).
- **What**: an author giving a sword "On Start" (`SELF_CYCLE_START`, the natural pick — the hero *is* the one starting) gets a correct-looking sentence and a rule that never fires; so do "On Cycle", "When Depleted", "On Kill" and the rest on an item. Worse, the id that *does* work, `CYCLE_START`, is the row labelled **"On Neighbour's Start"**, nearby-scoped (`triggerRegistry.js:228-236`), and the editor's patch stamps `scope: 'nearby'` from it (`statementSlots.js:535-539`) — the tests hand-write `{event:'CYCLE_START', scope:'self'}` (`CycleStart.test.js:141`, `CombatEngaged.test.js:145`) which the editor cannot produce. **No shipped item carries a timed rule today** (`data/items.json` has no `when`), so nothing is broken in play — this is a trap for the first author.

## 7. Owner questions

**Q1 — A crafted, bought or spawned Token with no charge count lasts forever
(CR3-045). What should the rule be?**

* **(a) Recommended — keep "no charge count = unlimited", and have the content
  audit flag it** whenever a Token that a recipe outputs or the Shop sells has
  no `uses`, so you decide per Token in the CMS. Nothing in the game changes
  until you author a number; the Woodaxe would appear on the audit list.
* (b) Make the craft/Shop routes refuse a Token with no `uses` (the Woodaxe
  recipe would stop working until it gets a number). Safe, but blocks play on
  half-authored content, which your standing rule says is normal.
* (c) Accept unlimited crafted Tokens as intended, and write that down where an
  author will read it. Cheapest; the Woodaxe stays permanent.

**Q2 — Should rule upkeep (an aura's "costs 1 Incense every 30 s") also take
matching loot lying on the mat, as spawner upkeep and recipe inputs do?**
(Already listed as open item 4 in `token_lifecycle_feedback_v1.md`.)

* **(a) Recommended — yes, Bank first then the floor**, through the same
  `InputAllocator` path. One meaning of "the thing it needs" everywhere; the
  Upkeep Summary gets simpler.
* (b) No — keep rule upkeep Bank-only (today's behaviour), and say so in the
  Upkeep Summary so the player isn't surprised.
* (c) Decide later, with the effects rework.

**Q3 — Which "when…" moments should a rule on an item have (CR3-202)?** Today
carried items fire only on *starting work* and *engaging an enemy*, but the
editor offers all ~13 moments.

* **(a) Recommended — only the two that work, for now**: the editor offers
  items just "On Start" and "On Engage" (named as the hero's own moments, not a
  neighbour's), and the audit flags any other. Small, honest, reversible.
* (b) Wire more moments into carried items (e.g. "On Cycle", "On Kill") — a
  design slice of its own.
* (c) Leave it; no item uses a timed rule yet.
