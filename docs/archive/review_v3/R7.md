## 1. Plain-language summary for the owner

- **Dragging mostly works, and the rules are in the right place.** Every drop ends in
  engine code (`Placement`, `MatPlacement`, `DiscardBin`, `Shop`, `EquipmentManager`). The
  screen never decides whether a Token may land. That is the opposite of round 2's CR2-033
  failure, and it is the most important thing this session checked.
- **One likely bug a player could hit (CR3-402).** The code says "a drawer beats the board
  where they overlap". That is only true where the drawer contains a drop target.
  Suppose you let go of a Token or a flag over the open Bank's header, the Shop drawer, or
  the hero sheet. It lands on the part of the mat **hidden underneath**. Only a Shop Token over
  the Shop drawer is caught.
- **The cost of a drag is not the pointer moving. It is the moment you pick something
  up or put it down (CR3-400).** The drag library re-draws *every* draggable thing on
  the screen when a drag starts, when it ends, and whenever the pointer crosses into a
  new drop target. On a full mat that is ~150 Tokens at once, and likely one dropped frame at
  165 Hz each time. It needs your hands to measure (Session C, items 1–2).
- **While you carry a Token, the "where will it land" preview runs twice every frame
  (CR3-401).** It is cheap on open ground. Over a crowded patch it gets slow, and it gets
  very slow near a Token with a "Cannot" rule (Coast / Shrimp Coast). A drag there may
  stutter. The fix is small.
- **Refused equips sound like successes (CR3-405).** You can drop an item on a hero that
  already carries it, or that has no free slot. You hear the equip sound and see
  nothing happen, and no message says why.
- **`PERFORMANCE.md`'s drag rules describe a system that no longer exists (CR3-406).**
  None of its three drag rules is followed by today's code, and the CSS they rely on is
  dead. Only one of them still matters: reading screen positions on every pointer move
  (CR3-403).
- **R8's hand-off was half right.** `cardSizeStore` is still imported by the drag
  ghost, but only through a card-frame ghost that nothing draws. It sizes nothing a player
  sees; the whole chain is dead code (CR3-407).
- **Mat size and zoom:** the pointer-to-mat maths is correct by construction at any
  mat size and any zoom, including the 0.1 floor. It is only tested at the default size
  (CR3-413). A real pointer drag at 6 and 20 steps still needs your hands (Session C item 11).

one mouse `pointermove` per frame (rAF-aligned), so "per move" ≈ "per frame" in practice.

**What does *not* run per move:** the collision is never a DOM read (rects are measured at
drag start; the `Optimized` frequency never re-measures, `core.esm.js:1961-2046`).
`MatBoard`'s hover pass bails out on `gi-dnd-active` (`MatBoard.jsx:196`). No engine state
changes until the drop.

**Flag or hero drag:** the same as above, except #5 is skipped (`MatRings` returns null for
non-Tokens) and #6 becomes `useFlagDragPoint`: a mat rect read, `Flags.tokenAtPoint` (one
`tokens()` walk) and `Flags.pinRefusal`, once per frame (`FlagLayer.jsx:111-129`). That is
cheap.

**Verdict:** the steady per-frame cost of carrying a Token over open ground is well under
1 ms. The two real risks are **#8/#9** (fan-out at pickup, drop and every target change)
and **#5/#6** over a crowded `Cannot` area. Neither can be measured from the preview pane
(§3.5 of the plan). Both have Session C items.

**Proposed drag rules for the rewritten doc** (R6 owns the rewrite; this is R7's section):

1. Nothing per pointer move touches the DOM. Measure at drag start; re-measure only on
   resize or scroll.
2. Anything that must follow the cursor reads `useDragPointer()` (one update per frame)
   and must be a leaf. Never put the pointer in a context that Tokens read.
3. Per-Token components must not call `useDraggable` in the component that renders the
   whole Token. dnd-kit re-renders every draggable on start, end and target change. Put
   the grab handle in a small memoised child, and signal "a drag is live" to per-Token
   art with the `gi-dnd-active` body class in CSS, not with `useActiveDrag()`.
4. A drop target's `accepts` only screens the payload kind. Legality lives in the
   engine, and `onDrop` returns `false` when the engine refuses.
5. The drag preview (landing ring) is computed once per frame, in one place.

### Drop routing — is every rule in the engine?

**Yes.** Every drop target ends in an engine call that decides legality (§8 table). UI
code decides only three things, and each is a gesture reading, not a game rule:

- **Board.jsx:61**: a Shop Token let go over the Shop drawer is a cancel (FB-27, geometry
  of a UI surface).
- **The Guild Hall's "cannot leave" warning** is UI (`MatToken.jsx:246-257`,
  `DragGhost.jsx:53-61`). The *prevention* is engine: `DiscardBin.canBin` refuses it
  (`DiscardBin.js:192`), and no other target accepts a Token.
- **`accepts` predicates** screen payload kinds only.

The failure shape round 2 feared is absent. The inverse shape is present: **an engine
refusal the UI ignores** (CR3-405).

### CR3-400 — Picking something up, putting it down, or crossing into a new drop target re-renders every draggable on the screen
- **Category / Severity / Effort**: RC · P2 · M
- **Impact / Confidence / Score**: 4 · 0.6 (reasoned) · 1.2
- **Risk**: medium — `MatToken` is the busiest component in the game; needs test: CR3-413 (drag start/end still hides and releases the carried Token)
- **Where**: `DndKit.jsx:410-418` (`useEntityDrag` → `useDraggable`); dnd-kit `core.esm.js:3337-3349` (`internalContext` holds `active` and `over`), `:3395-3403` (every `useDraggable` reads it), `:3476` (every `useDroppable`); `MatToken.jsx:240-260`; `MatBoard.jsx:70`, `:79-81`; `TokenEventAlert.jsx:435`; `SpriteLayerView.jsx:92`; `Board.jsx:54` (mat `useDroppable`, and `MatBoard` is not `React.memo`). Shared with R6 (board files).
- **What**: dnd-kit gives every draggable a context that changes when a drag starts, ends, or the hovered target changes. Each `MatToken` is a draggable, so all ~150 re-render at those moments; `React.memo` does not stop a context. `useActiveDrag()` in ~150 `TokenCentreAlert`s and every loot sprite adds a second wave at start and end. `MatBoard` commits twice at start (its hover-clearing effect). Dragging a Token across the dock's hero figures changes the target several times a second, and each change is another full wave.
- **Evidence**: code reading only. Estimate: 150 × `MatToken` body (hooks, layout maths, three child components) ≈ 5–20 ms per wave, i.e. at least one missed 6.06 ms frame per pickup and per drop.
- **Hypothesis to test**: Perf HUD `react.MatBoard` **max ms** during a pickup at S2 exceeds 6 ms. Commits per drag ≈ 3 + one per target change. Session C items 1–2.
- **Fix sketch**: move `useEntityDrag` into a small memoised `TokenGrab` child that owns only the handle div, so the rest of `MatToken` does not subscribe. Replace per-Token `useActiveDrag()` with a CSS rule on `body.gi-dnd-active`. Memoise `MatBoard`.
- **Owner session**: R7 (with R6)
- **Status**: 🔲 Open

### CR3-401 — While a Token is carried, its landing spot is worked out twice every frame, and near a `Cannot` rule each can be very slow
- **Category / Severity / Effort**: HPB · P2 · S
- **Impact / Confidence / Score**: 4 · 0.6 (reasoned) · 2.4
- **Risk**: low
- **Where**: `MatRings.jsx:50-64` (`useTokenDragLanding`), called by `MatRings.jsx:70` **and** `FlagLayer.jsx:165`; `MatPlacement.js:239-254` (`findSpot`), `:130-176` (`contextFor` walks `BoardState.tokens()`), `:211-221` (`legalIn` → `Restrictions.checkPlacement` when a `Cannot` is in range), `:460-469` (ring walk), `:48`, `:51` (4 u rings, 6 u arc); `matTuning.js` `nudgeReach` default 160; `Restrictions.js:62-69` (`snapshot` walks `tokens()`), `:206-212`
- **What**: the preview ring ("where it will land") is correct: it asks the engine, so it matches the drop. But both the Near ring and the flag rings compute it separately, every frame, with the same inputs. On open ground that is two `tokens()` walks (~50–60 µs at 150 Tokens). Over a crowded patch with no room, the ring walk tries up to ~3,400 candidates. If a Token carrying a `Cannot` rule is in range (today: **Coast** and **Shrimp Coast**, via `effect_placement_limit`), each candidate that is clear of neighbours builds a whole projected board. Worst case that is tens to hundreds of ms per call, twice a frame.
- **Evidence**: `tokens()` 22.9 µs per call at 150 Tokens (P2, measured); the candidate count follows from the ring constants; the rest is reasoned.
- **Hypothesis to test**: a micro-bench of `findSpot` at 150 Tokens, blocked spot, with and without a `Cannot` Token in range. Expect ~0.2–0.5 ms and >10 ms respectively. In game: Session C item 14.
- **Fix sketch**: compute the landing once per frame and share it (a small context beside `DragPointerContext`, or memoise on the rounded mat point). Skip the recompute when the pointer has moved < ~4 mat units. CR3-001 (cached Token list) shrinks both halves.
- **Owner session**: R7 (engine side R2)
- **Status**: 🔲 Open

### CR3-402 — A Token or flag let go over an open drawer or the hero sheet lands on the mat hidden underneath
- **Category / Severity / Effort**: WIRE · **P1** · S
- **Impact / Confidence / Score**: 4 · 0.6 (reasoned; Session C to confirm) · 2.4
- **Risk**: low — needs test: CR3-413
- **Where**: `DndKit.jsx:57-69` ("Drawers beat the board where they overlap", but the ranking applies only among **droppables**); `DndKit.jsx:111-129` (`surfaceAtPoint` knows the pointer is over a drawer, and uses it only for the ghost's shadow); `Board.jsx:58-67` (the only guard is Shop-payload-over-Shop-drawer); `ShopDrawer.jsx:38-51` (the drawer is deliberately not a droppable); `BottomFolderDrawer.jsx:75-87` ("covering … the playmat"); `BankTab.jsx:246`, `:311`, `:384` (only the item list, tiles and tab buttons are droppables); `BottomHeroDock.jsx:106-128` (the dock's droppable rect is the strip; the hero sheet overflows it)

- **Fix sketch**: in `Board.jsx`'s `onDrop`, treat `surfaceAtPoint(pointer) === DRAWER` the way the Shop check is treated: return `false`, so the drop flies back. That is one line, generalising FB-27. Owner question Q1 picks the behaviour.
- **Owner session**: R7
- **Status**: 🔲 Open

### CR3-403 — The drag reads the page's layout on every pointer move
- **Category / Severity / Effort**: PNT · P2 · S
- **Impact / Confidence / Score**: 2 · 0.6 (reasoned) · 1.2
- **Risk**: low
- **Where**: `DndKit.jsx:196-216` (un-throttled window `pointermove`), `:111-129` (`surfaceAtPoint`: two whole-document `querySelectorAll`, ~5 `getBoundingClientRect`); `MatRings.jsx:55` and `FlagLayer.jsx:120` (mat rect read per frame, per component)
- **What**: to decide whether the ghost's shadow is "bold" (over the board) or "compact" (over a drawer), the provider queries the whole page and measures every drawer on every pointer move. When the mat has just moved something, which is most frames while heroes walk, the first measurement forces the browser to lay the page out immediately, inside the input handler. The mat's own box is also re-measured every frame by two components, though it cannot move during a drag (a window resize cancels the drag, `core.esm.js:1444`).
- **Evidence**: code reading; cost scales with page size (~3–4k nodes at S2). R6 owns the layout cost itself (CR3-007).
- **Fix sketch**: take `surface` from the collision (`handleDragOver`, which fires only when the target changes: `over.data.current.surface`), or measure region rects once at drag start. Measure the mat rect once at drag start and share it. Delete the miniboard query (CR3-407).
- **Owner session**: R7
- **Status**: 🔲 Open

### CR3-404 — The drag provider renders the drag library twice a frame
- **Category / Severity / Effort**: RC · P3 · S
- **Impact / Confidence / Score**: 1 · 0.6 (reasoned) · 0.6
- **Risk**: low
- **Where**: `DndKit.jsx:185-205` (per-frame `setDragPointer` in the provider), `:369-399` (`DndContext` a child of that render), `:325` (`dropAnimation` object) and `:379` (`autoScroll` object) rebuilt every render
- **What**: dnd-kit already re-renders on each pointer move. The provider then re-renders once more per frame to publish the cursor, which re-renders dnd-kit, recomputes the collision, and redraws the ghost a second time.

### Pointer → mat

`pointerToMat(pointer, matEl.getBoundingClientRect())` = `(pointer − rect.corner) ÷ (rect.width ÷ matW())`
(`matPoint.js:27-34`). The mat element is drawn at `mat.w × mat.h` (`useMatSize`) and
CSS-scaled by `fit.scale` (`useBoardScale`: two-axis, floored to whole percent, floor 0.1,
`useBoardScale.js:89-105`). Every caller measures the same box: the drop (`Board.jsx:63`),
the hover (`MatBoard.jsx:214`) and the previews (`MatRings.jsx:55`, `FlagLayer.jsx:120`).
Grab offset is 0 because the ghost is centred on the cursor. Correct at any size and zoom;
tested only at 11 steps (CR3-413).

### Disallow mode

A module-level flag with `useSyncExternalStore` (`useDisallowMode.js:17-43`). While on:
drags that start inside `[data-board-origin]` are refused at the sensor
(`DndKit.jsx:164`), a Token click flips it (`MatToken.jsx:435`), and `MatBoard` draws the
red edge. It is never saved, and it turns off when the bar unmounts
(`MatDisallowControls.jsx:35`). Dock, Bank and Shop drags still work (owner, 2026-09-27).
