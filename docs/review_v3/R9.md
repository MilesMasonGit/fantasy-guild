## 1. Plain-language summary for the owner

- **The word "tile" is mostly harmless now.** About a third of it is the
  switched-off terrain painter, art folder names and the table-texture setting —
  those stay. The rest is old naming inside the engine (a module called
  `TileModifiers`, events called `TILE_CHANGED`…). Renaming them is a safe,
  mechanical, one-sitting job, and there is a ready list of every place to change.
- **Players can still read "tile" in the rules text.** A Token that leaves
  something behind says it does so *"on this Token's tile"*, and two other
  wordings say *"the nearest free tile"*. The Token editor also tells you a
  "nearby" rule reaches *"the 8 surrounding tiles"* — that is now wrong, it
  is a distance. I've asked you to pick the replacement wording (Q1).
- **The Tray is gone from saves but its name survives in ~34 files.** Only one
  piece of it must stay (the part that cleans Tray data out of older saves). The
  rest is leftover names and, worse, comments that still describe the Tray as if
  it existed — which misleads the next agent.
- **The instructions other AI agents follow are the biggest risk here.** The
  `.agent/` folder (read automatically by Gemini-style agents) still tells
  agents how to "add a Card", "add a Tile" and "add an Item by editing the code" —
  that last one would be wiped out by the editor's sync. The shared rules file
  for director agents describes the project as it was on 2026-08-20. I've
  sorted every document into *keep*, *fix* or *archive* (Q3, Q4).
- **The dead-code finder has a fourth blind spot.** A comment that contains an
  apostrophe right before an import makes it miss that import. That's why it
  has always called the hero-name list "dead" — not the reason everyone wrote
  down. The same flaw is in the import-cycle checker. Small, cheap fix.
- **The game file is 1.15 MB, and splitting it would not help a desktop game.**
  Almost 40 % is React and the animation/drag libraries. About 36 KB is
  developer-only screens. The five font packages listed as dependencies aren't
  used at all (the fonts are copied into the project) — safe to tidy.
- **The build quietly ships art you haven't decided to keep.** It copies the
  `archive`, `maybe` and `waste` art folders (60 images) into the game and even
  pre-loads them at start-up, because the build reads whatever is on disk.
- **The layers are clean where it matters:** no engine file touches React. The
  weak spots are softer — the UI calls engine commands directly in many
  places, and some content (the starting mat, the tutorial quests) is written
  into engine code rather than the editor.

## 3. Tile / tray classification

Verdicts: **Legit** = legitimate, keep · **Save** = save-compatibility, must
stay · **Residue** = rename or delete. Counts are *occurrences (in code)*.

### 3.1 Save compatibility — what old saves actually carry

- **No `tile` field survives in any loadable save.** Schema `0.8.0` stores
  Tokens by point and **refuses** every older save (`SaveMigration.js:29-35`,
  `StateSchema.js:27-37`). Every `tile` hit in those two files is a comment.
- **Tray:** `SaveMigration.js:93-127` strips `tray`, `nextTrayZ` (and the Vault
  fields) from 0.8.0 saves written before Token Lifecycle 9.3 — the schema was
  **not** bumped for 9.3, so such saves exist. **Keep** `RETIRED_BOARD_FIELDS`.
- **Settings (localStorage, not the save):** `ui.backgroundTile` is a live
  setting and stays; `ui.tooltipsBoostTiles` and `ui.largeTrayTokens` are dead
  settings (CR3-033) — removing them from the defaults leaves a harmless stale
  key in old settings *(reasoned)*.
- **Content data:** `data/*.json` contains **no** `tile` string at all, so no
  authored content depends on any tile-named id or event value.
