# P3: the in-game performance harness (Tier B)

*Round-3 code review, preparation session P3, 2026-09-28. Branch `tool/perf-hud`.
Plan: `code_review_v3_master_plan.md` §4.2.*

## In plain language

The headless benchmark (P2) times the game's rules with no screen. This session
built the other half: a way to measure the game **while it is drawing**, inside
the real window.

- **Stress boards.** One link, `?stress=realistic`, builds a busy late-game
  board (8 heroes, about 106 Tokens, goblins walking) and starts it running.
  These are the same five boards the benchmark uses (S1–S5). The code is shared,
  not copied: if a board changes in the benchmark, it changes here too.
- **A Perf HUD.** A small black box in the bottom-left corner. It shows how long
  each frame takes, whether any frame froze, how long each game tick takes, how
  often the main parts of the screen redraw, and a few leak signs (page size,
  listener count, memory).
- **A "Copy report" button.** It copies every number as one block of text. You
  paste that into a chat and an agent can read it.
- **Dev builds only.** None of this exists in the game a player gets. I built
  the shipped version and searched it, and found nothing (details at the end).

**Your saves are safe.** Starting a stress board never writes to a save slot.
If a game is loaded, it is saved once and then left alone. Your settings and
Mat Tuner values are put back as they were. Reload the page to get your game
back.

## How to use it

| To… | Do this |
|---|---|
| Run a stress board | Open the game with `?stress=<name>` on the address, e.g. `http://localhost:5173/?stress=realistic`. The HUD appears on its own. |
| Names | `quiet` (S1), `realistic` (S2), `torture` (S3), `push` (S4), `rebuild` (S5). `S1`…`S5` also work. |
| Use the QA panel instead | QA button (bottom right) → **Performance** → a scenario button. If a game is loaded it asks first. |
| Turn the HUD on or off | QA panel → **Toggle Perf HUD**, or the HUD's **Hide** button. It stays on after a reload until you hide it. |
| Start the numbers again | The HUD's **Reset** button (for example, after the board has settled). |
| Hand the numbers over | **Copy report**, then paste into the chat. |

### Reading the HUD

```
PERF HUD  S2 realistic  ·  62 s
frame Δ   p50 6.06  p95 6.10  p99 8.30  max 33.0 ms  ~165 Hz
  over 6.06: 120  8.33: 20  16.7: 3  of 10,000  (98.8% ≤ 6.06)
frame work p50 2.10  p95 3.90  p99 5.20  max 30.0 ms (est.)
LoAF 3  max 72 ms  top: user-callback TimerHandler:setInterval @ src/…
tick p50 0.41  p99 1.20  max 3.10 ms  · 10.0/s
react/s  mat subtree commits 0.5 (MatBoard itself 0.3)  dock 1.0  drawer 0.0  bar 0.5
events/s 340  listeners 612  DOM 2,140  heap 84 MB
```
*(The example numbers are made up, to show the layout.)*

- **frame Δ**: the time between one frame and the next. On a 165 Hz screen a
  perfect frame is 6.06 ms. On a 60 Hz screen every frame is at least 16.7 ms
  whatever the code does (plan §2.B), so read the next line instead.
- **frame work (est.)**: roughly how long the computer spent on each frame. This
  does not depend on the screen, so it answers "does a frame fit in 6.06 ms?"
  even on a 60 Hz monitor. It is an estimate: anything else that runs during the
  frame is counted too.
- **LoAF**: Long Animation Frames. These are frames that took over 50 ms, which
  you would see as a stutter. `top` names the code responsible.
- **tick**: how long one game-rules tick took (10 a second).
- **react/s**: how many times a second each part of the screen redrew: the mat,
  the hero dock, the drawer, the top bar. ⚠ **"mat subtree commits"** counts
  every redraw of anything *on* the mat (one hero's walking frame counts);
  **"MatBoard itself"** is how often the mat as a whole redrew (CR3-311). Read
  the second one for "does the mat re-render?". If it says "off", reload with the HUD
  on (see "Design notes" below for why).
- **⚠ hidden N s** in the title: the window was minimised or behind another
  window. Those numbers do not count, so run again.

## For agents: `window.__perf`

| Call | Returns |
|---|---|
| `await __perf.start('realistic')` | Builds the scenario (replacing the game in this tab) and starts measuring. With no name, measures the current game. |
| `__perf.report()` | Plain JSON: `scenario` (built, build ms, census; S4 adds `operations`, the timed drops, arrivals and shrink), `window` (start, end, seconds, hidden seconds, `representative`), `env` (`userAgent`, `refreshHzEstimate`, DPR, viewport, build), `census`, `frames` (p50/p95/p99/p99.9/max, `over` and `pctAtOrUnder` at 6.06/8.33/16.7, `missedVsync`, `recent`), `frameWork`, `longAnimationFrames` (count, max, `topScripts`, the 10 `worst` frames with their scripts), `tick`, `react` (per surface: commits, per second, total and max ms; the `MatBoard` surface is the mat *subtree*, and `react.ownRenders.MatBoard` is MatBoard's own renders, CR3-311), `events` (per second, listener calls, top 25 by name), `dom`, `listeners`, `heap`. |
| `__perf.reset()` / `__perf.stop()` | Start a new window. Stop removes every wrapper, observer and timer. |
| `__perf.showHud()` / `hideHud()` / `toggleHud()` | The overlay. |
| `await __perf.drive(n)` | Runs `n` 100 ms ticks through the real `GameLoop.runHandlers`, in chunks, for panes where the loop is throttled. |
| `__perf.snapshot()` | What the HUD shows right now. |

A report is about 7 KB of JSON.

### Design notes

- **When the HUD is off, nothing is installed.** There is no animation-frame
  loop, observer, wrapper or timer. The Profilers are not in the page either,
  unless it was loaded armed. Hiding the HUD leaves them in place until the
  next reload; they only add to counters that nothing reads. I
  checked this in the game: after Hide, `EventBus.publish` and
  `GameLoop.runHandlers` are the originals again, and no `fg-perf:tick` timing
  entries are left.
- **Why the Profilers are "armed" only at page load.** The redraw counters use
  React's Profiler, a measuring wrapper around each part of the screen. Adding
  or removing one mid-session would rebuild the whole mat, lose its state and
  spoil the numbers being read. So they are switched on only by `?stress=`,
  `?perf=1` or a remembered HUD. If you turn the HUD on mid-session, the redraw
  line says to reload.
- **The HUD does not grow.** Frame and tick times go into fixed histograms (0.01
  ms / 0.001 ms buckets). Timing entries are cleared every 2 s, so a 60-minute
  soak does not pile up 36,000 of them. The per-name tables stop adding new
  names at 200.
- **Scenarios run on default Mat Tuner values**, as the bench does. They are
  reset for the page only and your stored values are put back. The report's
  `scenario.matTuningWasCustom` says whether yours differed.
- **Not identical to the bench, on purpose.** The game uses real randomness and
  the real clock, so two runs do not do exactly the same work. S6 (long idle) is
  not offered: in the game, the soak test is S2 left running.
- **Debug Mode in a shipped build does not get the harness.** The existing QA
  surfaces show when `import.meta.env.DEV || debugMode`. The harness is
  compile-time `DEV` only, so the production-build check below can pass. See
  question P3-Q1.

## Session C: the owner's certification checklist (draft, about 15 minutes)

*Do this on the reference machine, in a real focused window: the desktop app
(`npm run tauri:dev`) or Chrome/Edge at `npm run dev`. Keep the game window in
front and do not use the computer while it runs.*

1. **Start the game.** In a terminal in the project folder, run `npm run dev`
   (or `npm run tauri:dev` for the desktop app) and wait until it says "ready".
2. **Open the realistic board.** Go to `http://localhost:5173/?stress=realistic`.
   In the desktop app, open the QA panel → Performance → **S2 Realistic**. The
   slot picker should close by itself, and a busy board with 8 heroes should
   appear with the Perf HUD in the bottom-left corner. If the HUD's redraw line
   says "off", reload the page.
3. **Let it settle.** Wait about 30 seconds, then press **Reset** on the HUD.
4. **Leave it for 5 minutes.** Don't move the mouse over the game or switch
   windows. If the HUD title shows "⚠ hidden", the window lost focus, so press
   Reset and start the 5 minutes again.
5. **Copy report** → paste it into the chat with the words "S2, 5 minutes".
6. **Torture test.** Change the address to `?stress=torture` (or press **S3
   Torture**). Wait 30 s, press Reset, wait 5 minutes, then **Copy report** →
   paste it with "S3, 5 minutes".
7. *(Optional, 1 minute)* Tell the agent your monitor's refresh rate (Windows:
   Settings → Display → Advanced display). The report estimates it, but you know
   it for sure.

**What the agent checks against plan §4.4:** at least 99 % of S2 frames at or
under 6.06 ms (on a 165 Hz screen, from `frames`; on a slower one, from
`frameWork`); p99.9 at or under 16.7 ms; no Long Animation Frames over 50 ms;
at least 95 % for S3; and MatBoard redraws per second.

### The 60-minute soak (Tier C, plan §4.3): a separate sitting

Run step 2 with `?stress=realistic`, press Reset, and leave the window in front
for 60 minutes. Press **Copy report** at 5, 30 and 60 minutes, without
resetting in between. Each report's `dom`, `listeners` and `heap` carry the
start, low, high and current values. ⚠ The HUD's heap number is **not** taken
after a garbage-collection pass (a clean-up that frees unused memory), which
the §4.4 memory check needs. For that, open DevTools → Memory, click the bin
icon ("Collect garbage"), and note the number at 5 and 60 minutes. Heap
snapshots at 5 and 60 minutes, compared, are the stronger check (plan §4.3).

## What the preview pane showed (⚠ NOT REPRESENTATIVE)

The agent's preview pane is a hidden, throttled browser pane on a busy
machine. It runs the React **development** build, with four review agents
benchmarking on the same computer at the same time. **These numbers prove the
plumbing works. They are not measurements of the game.**

- `?stress=realistic` built S2 in about 160–180 ms: 106 Tokens (40 placed, 66
  spawned), 6 goblins, 8 heroes. The slot picker closed and `currentSlot`
  stayed `null` (nothing saved). The HUD appeared, and `window.__perf.report()`
  returned about 7 KB of JSON.
- A 74-second S2 window (the pane happened to be drawing, `representative:
  true` by the tool's own test, which is still not representative of a real
  window):
  - frames: 5,946, interval p50 12.1 ms, estimated refresh "82 Hz" (the pane is
    throttled);
  - frame work (est.): p50 5.9, p95 11.3, p99 20.0 ms;
  - Long Animation Frames: 12, worst 140 ms, top attribution React's scheduler
    (`performWorkUntilDeadline`);
  - tick: p50 1.2, p99 6.8, max 10.3 ms, 10.0 ticks a second;
  - React commits per second: MatBoard 36.6, HeroDock 28.6, TopBar 0.44,
    Drawer 0;
  - events: 58 a second, 480 subscriber calls a second; about 1,475 DOM nodes,
    about 831 listeners, heap about 58–73 MB.
- **LoAF attribution works.** A deliberate 120 ms busy loop in an animation
  frame was caught as a 126.7 ms Long Animation Frame, blamed on
  `user-callback FrameRequestCallback`. Game ticks are blamed on
  `TimerHandler:setInterval @ src/systems/core/GameLoop.js`.
- **`drive(200)`** ran 200 ticks, and all of them were counted in `tick`.
- **All five scenarios built** through `__perf.start`: S1 6 Tokens (3 ms), S2
  106, S3 320 (1.7 s), S4 135 plus its timed operations (50/50 arrivals landed,
  0/50 hand drops landed, which is the refusal case; worst operation 68 ms,
  shrink 463 ms, dev build, not representative), S5 107.
- **Storage kept.** A custom Mat Tuner value planted in `localStorage` was
  byte-identical after building S3 and then S2, and so was the settings key.
- **Copy report** said "Copied". Reading the clipboard back is not allowed in
  the pane, so the paste itself was not checked.

**One thing worth a reviewer's look** (it is a count, not a timing, so the
throttled pane matters less): **MatBoard committed about 37–49 times a second
on S2**. Plan §4.4's target is at most 1 a second while heroes work, and none
from walking. The top event was `board:progress`, at about 37 a second. This
is from a dev build in a pane, so I have not filed it as a finding. It is for
R-sessions and Session C to confirm on a real window.

## Parked for the owner

**P3-Q1: should the harness also work in a shipped build with Debug Mode on?**
- **(A) No, dev builds only, as built. *Recommended.*** The shipped game stays
  clean, and `tauri:dev` already runs the real desktop engine (WebView2) with
  the harness.
- (B) Yes, behind Debug Mode. You could measure the exact build players get, but
  the harness code would ship to players, switched off.

**P3-Q2: certify frames on the development build, or add a "profiling build"?**
The dev build runs React's development mode, which is noticeably slower than
what players get. So Session C's frame numbers will be pessimistic, and a
borderline S2 could fail when the real game would pass.
- **(A) Certify on the dev build now, and treat a near miss as "re-check".
  *Recommended for now.*** No extra work. If S2 lands close to the 99 % line, do
  (B) before ruling.
- (B) Add a small `npm run build:perf` (a production build with React's
  profiling mode and the harness left in, never shipped). The numbers match what
  players get, at the cost of one more build to maintain. It would be its own
  small ticket.
