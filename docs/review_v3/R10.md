## 1. Plain-language summary for the owner

- **Most of the risky fixes already have a test to stand on, but not a gate.**
  Reviewers R2 and R3 proved their speed fixes change nothing by comparing a
  "fingerprint" of the finished game, plus a position checksum. That comparison was
  done by hand in a throwaway copy. The benchmark does record a fingerprint, but
  - it only checks that repeat runs agree with *each other*, never with the saved
    baseline, and
  - it is a handful of totals, not the positions.

  So today **a speed fix could quietly change the game and the tripwire would stay
  green.** §3 describes the exact change to the bench that closes this (CR3-550).
- **Of the 15 player-facing or measured "P1" tickets, none is safe to fix blind.**
  - 12 need a small test written first. Most are 10–30 lines, and the setup already
    exists in another test.
  - 3 need your eyes, because they change how something looks.

  Several of the new tests are written to **fail today and pass after the fix**,
  so they prove the bug and the cure: the dock HP bar, the new-game save, and the
  hero sheet beside the Bank.
- **Some fixes will break tests on purpose, and that is fine if it is planned.**
  - Changing how Tokens and heroes are moved on screen (R6's CR3-007) breaks about
    37 test checks that read the old `left`/`top` numbers.
  - Cutting the combat↔flags import loop (CR3-157) breaks three test files whose
    setup never switches on the part that would do the work.

  Update those tests first (CR3-556, CR3-557).
- **Several features are proven only by pretend test content.** The real content
  (94 Tokens, 64 items, 22 library effects) has:
  - no whole-mat buff,
  - no input-cost discount,
  - no status or timed effect,
  - no item carrying any rule.

  So fixes in those areas (CR3-004's aura half, CR3-028, CR3-102, CR3-250's big
  number, CR3-251/252/253) change **nothing** a player can see today. They are
  still worth doing, but they are not player-urgent (CR3-551).
- **The 10 known test failures are all "content moved, the test didn't".** None is
  an engine bug. Six are the dormant terrain system's hand-written table, which
  lists 75 Tokens while the game now has 94. I recommend marking them as known
  failures in the test file itself, so a *new* failure turns the suite red at once
  instead of being spotted by eye (CR3-553, Q1).
- **19 test files can't run in a fresh copy of the project** because the editor's
  packages aren't copied in. The fix is one extra folder link when a copy is made
  (CR3-552, Q2).
- **Stage 2 (heroes deciding more for themselves) has one good seam and one messy
  one.**
  - Good: every change to what a hero is working happens in one file (`Flags.js`).
    That file is also the only one that tells the walking code to start, stop or
    go home.
  - Messy: "what state is this hero in?" is spread over seven places, with two
    different vocabularies (CR3-561).
- **Stage 3 (biomes) cannot be added through the editor today.**
  - Terrain is switched off, and written in code by your own ruling (D-T9).
  - It is still shaped for the old grid.
  - It has nowhere to be saved.

  Growth, spawning and wandering, on the other hand, are already authored in the
  editor (CR3-564).
- **Type-checking would catch some real problems, but none of the P1 bugs.** It
  would have caught:
  - event messages missing fields;
  - the Guild Hall definition being overwritten on load;
  - the "never change the shared Token list" rule that the biggest speed fix
    relies on.

  It would not have caught the save, clock, HP-bar or drop bugs. It is worth a
  one-sitting trial later, not now (CR3-560).

## 3. "Identical results" as a permanent gate

### 3.1 What exists today

- `bench/lib/harness.mjs:230-249` `fingerprint()` returns:
  - totals: Token count, summed `usesRemaining`, summed Bank quantity, summed hero XP;
  - the sprite count and `gameTimeMs`.
- `bench/run.mjs:116-119` `sameWork` only checks that the **repeats of one run**
  agree with each other.
- `comparable()` (`:170-174`) and `compare()` (`:176-196`) compare **timings only**.
  The baseline file stores only `p50`/`p99` or `worstDropMs`/`shrinkMs` (`:296-302`).
- The S4 position checksum R2 used (a hash of every `id,x,y`) lived only in a
  scratch worktree.
- Randomness is seeded at the process boundary (`bench/lib/prelude.mjs:20-37`), so a
  scenario is deterministic on one Node version.

**Two weaknesses.**
1. A fingerprint change is never compared with the baseline.
2. The fingerprint is **totals**. A fix that moves a Token, reorders two spawns or
   swaps which Token got the buff can keep every total identical.

### 3.2 Proposed change (for the director; R10 edits no bench file)

1. **A strong fingerprint**, next to the existing one (keep the old fields for
   readability). Each hash is a stable string hash (FNV-1a is enough):
   - `tokensHash`: `id|typeId|x|y|usesRemaining|placedAt`, in `tokens()` order.
     Coordinates as exact numbers, not rounded; R2 showed the solver fixes are
     bit-identical.
   - `bankHash`: `itemId:qty`, sorted by id.
   - `heroHash`: `heroId|skill:xp|…|hp.current|flag x,y|claim instanceId`, sorted.
   - `spriteHash`: `itemId|qty|x|y`.
   - **`randomDraws`**: count calls in the seeded generator
     (`prelude.mjs:24-30`). This is the most sensitive single number. Any fix that
     consumes randomness in a different order changes it, even when the end state
     happens to match — which is exactly R3's CR3-201 warning about
     `pickWeighted`.
2. **S4's checkpoints**: `positionsAfterArrivals` and `positionsAfterShrink`
   (the same `tokensHash`), returned from `custom()`.
3. **The baseline stores them.** `--save-baseline` writes, per scenario,
   `identity: { …strongFingerprint, randomDraws }` beside the timing numbers.
4. **`--compare` fails on any identity difference**, with its own verdict,
   `WORK CHANGED` (distinct from `REGRESSED`):
   - it prints both values and names the differing fields;
   - exit code 2, so a timing regression (1) and a behaviour change (2) are told
     apart.
5. **A deliberate change** (a ruled behaviour change such as Q2 of R2) needs
   `--accept-work-change="<ticket>"`. That rewrites only the identity block and
   records the ticket and the commit in `baseline.json`'s meta. No silent rebaseline.
6. **Portability.** If `process.version` differs from the baseline's `meta.node`,
   print "Node changed — identity may differ for reasons outside the code", and
   still fail. The owner re-takes the baseline on a Node upgrade.
7. **Speed.** Identity comes from the timing runs already made (`--no-profile` is
   enough). No extra run is needed, and `sameWork` stays as a first check.
8. **The merge rule** (§10 of the plan) becomes: test baseline unchanged, **and**
   `npm run bench -- --compare` exits 0. That means no timing regression **and** no
   work change.

The vitest position golden of §2.1 (CR3-003/150) duplicates part of this, on
purpose. `npm test` runs on every merge, while the bench takes about 3 minutes.

## 5. Stage 2 seams (autonomous heroes) — described, not designed

⚠ **Vocabulary drift first.** The concept's "Stage 2 — Autonomous heroes" row
(`docs/concept_free_playmat.md:52`: walking, claiming, nearest-first choice,

replaced it (`docs/hero_movement_roadmap_v1.md:10-12`). "Stage 2" in this review
therefore means what is still open: heroes deciding beyond their flag (the owner's
"fish in a tank" list), steering (HM-3 left the door open), hostile reactions, and
multi-step jobs.

### 5.1 Where "decide what to do next" lives

**In one file: `Flags.js`.**

- `assign` (`:749-771`) runs each tick, in planting order:
  1. `lapsePins` (`:723-736`);
  2. `keepOrRelease` for heroes holding a claim (`:612-721`);
  3. `choose` for the rest (`:565-590`), which calls `evaluate` (`:489-562`).
- `evaluate` is the whole policy: under-the-point kinds, then in-radius candidates
  sorted by priority → distance from the hero → `placedAt`, then 7 skip checks,
  `WorkCheck` last.
- **Flags is the single writer of claims.** Every `setClaim`/`claimToken` is in
  `Flags.js` (`:349`, `:359`, `:577`, `:596`, `:690`, `:704`, `:709`, `:1071`,
  `:1248`).
- **Flags is the only caller of HeroMotion's lifecycle**: `settle` (`:351`, `:377`,
  `:884`), `enter` (`:882`), `sendHome` (`:1030`), `restoreAtWork` and
  `placeAtFlag` (`:1247-1251`).
- Other modules reach a hero's decision only through Flags:
  - `Hostiles.tick` → `Flags.ambush` (`Hostiles.js:129`);
  - `BoardCombat.resolveDefeat` → `Flags.furl` (`BoardCombat.js:581`);
  - `Placement` → `Flags.plant` / `furl` (`Placement.js:447`, `:464`).

**This is the good seam.** A Stage-2 policy change goes in `evaluate` /
`keepOrRelease`, and nothing else writes a claim.

### 5.2 Is there one hero state machine? No — seven stores and two vocabularies

| Store | Holds | Written by |
|---|---|---|
| `board.flags[heroId]` (saved) | flag point, `pinnedTo`, `plantedAt` | Flags (via BoardState) |
| per-board runtime `claims` (`BoardState.js:380-403`) + `board.workClaims` (saved, HM-7) | what the hero is walking to or working | Flags only |
| Flags runtime in the same record: `skips`, `nextTryAt`, `notified`, `cycleEnded`, `ambushes`, `clock`, `dirty` | the decision's memory | Flags |
| HeroMotion body in the same record (`bodies`) | position, target, side, `atWork`, `potter`, `homeward`, `limp` | HeroMotion (`:198-231`, `:401-421`) |
| `hero.status` on the hero object (saved) | **`idle` / `combat` / `wounded`**, a second vocabulary | `CombatProcessor.js:85`, `CombatResolutionProcessor.js:8`, `:64`, `WoundedSystem.js:87`, `:114`, `BoardCombat.js:570`; `HeroGenerator.js:196` |
| `BoardCombat` fights Map (not saved) | `fightOfHero` | BoardCombat |
| Promotion offer on the Token (`promotionPaused`/`promotionHeroId`) | a paused offer | BoardPromotion |

- `Flags.statusOf` (`:1149-1185`) **derives** the player-facing state
  (`docked`/`returning`/`working`/`walking`/`idle`) from four of these.
- `hero.status` is separate, and is read directly by `BoardRunner.js:832`,
  `Hostiles.js:68`, `LiveEffects.js:106` and `StatusEffectSystem.js:110`.
- There is **no explicit state enum and no transition table**. The "mode" is
  implicit in which Maps hold the hero's id.
- The good news: every runtime store is already **one record per board**
  (`flagRuntime()`, `BoardState.js:406-409`), so the pieces are in one place, just
  not in one shape (CR3-561).

### 5.3 What walking AI would have to change (seams, not designs)

- **`Flags.evaluate`'s search area is the flag.**
  - `point` is the flag (`:490`), reach is `flagReaches(flag, centre)`, and "nearest"
    is measured from the hero (HM-4).
  - A hero choosing without a flag, or with a roaming area, needs the search area as
    an **input** (centre, radius, or a policy object) rather than read from
    `flagOf`.
  - `choose` returns early with no flag (`:567`) (CR3-562).
- **The claim is one instance id.** `{instanceId, typeId, x, y}` (`Flags.js:359`).
  A multi-step job ("fetch the ore, then smelt") has nowhere to live: the claim
  model, `workClaims` in the save and `statusOf` would all need a task field.
- **`HERO_MOVED` means "the claim changed", not "the hero moved".**
  - It triggers neighbourhood rebuilds (`TileModifiers.js:125-131`, CR3-250) and six
    UI subscribers.
  - More autonomous re-choosing means more of these. Its payload names only the new
    Token; R5 (CR3-304) wants `fromInstanceId`.
- **HeroMotion is a pure "where to go" (`destinationOf`, `:198-231`) plus a
  straight-line `step`.** Steering around Tokens (HM-3's "later") would need a
  spatial query per step, which is CR3-003/152's index territory. Every hero step
  must also stay off the neighbour-cache invalidation path (only enemies call
  `setTokenPoint`; heroes are bodies, which is good).
- **Retry and dirty.**
  - One board-wide `dirty` flag re-runs every idle flag (`Flags.js:1267-1285`:
    `TILE_CHANGED`, `TOKEN_PLACED`, `inventory_updated`).
  - Cheap today (0.19 evaluations a tick, P2), but it scales with how often heroes
    choose. More autonomy puts CR3-001 (the cached list) on the critical path.
- **Headless runs.** The engine starts only on a React event (CR3-307). An AI
  simulation, or a Stage-2 bench scenario, needs `Engine.startSlot`.
- **One command surface** (R9 CR3-512, R5-Q2). AI and UI already call the same
  engine commands (`Placement.plantFlagAt` etc.). Keep it that way: AI must never
  call `BoardState.setClaim`.
- **Randomness** (CR3-563). A chooser with random tie-breaks needs an injectable
  RNG to be testable and bench-deterministic.

- **`isGuildHall` is copied in 5 places** (R2 CR3-155). A second "home" building (a
